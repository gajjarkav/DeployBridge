# Phase 4 Report

## Introduction

Phase 4 of DeployBridge expanded GitHub Pages deployment from plain HTML, CSS, and JavaScript repositories to a broader set of static-site workflows. This phase introduced framework-aware detection, workflow selection, and deployment logic so that supported repositories can be published to GitHub Pages through GitHub Actions custom workflows.

## Work Completed in Phase 4

The following work was completed during this phase:

- Replaced the static-only deployment validation with profile-based repository detection.
- Added support for multiple GitHub Pages deployment profiles.
- Added profile-specific workflow template generation for GitHub Actions.
- Added a detection API so the frontend can preview the detected deployment profile.
- Added optional manual override support for deployment profile selection.
- Extended deployment responses to return the resolved profile and workflow template.
- Added support documentation for framework detection and workflow behavior.
- Preserved the existing static HTML deployment path for no-build repositories.

## Supported Deployment Profiles

Phase 4 supports the following GitHub Pages deployment profiles:

- `html` for plain static HTML, CSS, and JavaScript repositories.
- `jekyll` for Jekyll repositories with `_config.yml`, `_posts`, or a Gemfile-based setup.
- `node-static` for Node-based static site builds such as React, Vite, Vue, Astro, Gatsby, Angular static builds, and Nuxt static generation.
- `next-static` for Next.js repositories that are configured for static export.

## Backend Setup

The backend deployment service was upgraded to support framework-aware GitHub Pages deployment. It now includes:

- Repository profile detection based on repository files, directories, dependencies, and scripts.
- A deployment profile registry that maps a profile to a workflow template and deployment behavior.
- Detection and deploy API support for both auto-detection and manual override.
- Workflow cleanup logic so stale DeployBridge workflow files do not remain active after profile changes.
- Profile-specific deployment responses for better frontend visibility.

## Frontend Setup

The frontend dashboard deployment flow was updated to support framework deployment. It now includes:

- A detection request before deployment.
- A prompt showing the detected deployment profile and reason.
- Manual profile override support before the deploy request is sent.
- Improved deployment alerts showing the resolved profile and selected workflow template.
- Clearer error handling for unsupported repositories and invalid overrides.

## Workflow Templates Added

Phase 4 added these workflow templates:

- `html.yml`
- `jekyll.yml`
- `node-static.yml`
- `next-static.yml`

All templates use GitHub Pages Actions publishing with:

- `actions/checkout`
- `actions/configure-pages`
- `actions/upload-pages-artifact`
- `actions/deploy-pages`

The build-oriented templates also include framework-specific install and build steps before artifact upload.

## Technologies Used in Phase 4

The following technologies were used in this phase:

- FastAPI for detection and deployment APIs
- GitHub REST API for repository inspection, workflow file creation, and Pages setup
- GitHub Actions for build and publish workflows
- HTTPX for GitHub API requests
- Pydantic for request and response models
- HTML, CSS, and JavaScript for the frontend deployment experience

## Conclusion

Phase 4 upgraded DeployBridge from a plain static-site publisher into a framework-aware GitHub Pages deployment bridge for static-output repositories. It now supports multiple static deployment profiles, deployment profile detection, manual override, and per-framework GitHub Actions workflows while keeping SSR and server-based deployment out of scope for this phase.
